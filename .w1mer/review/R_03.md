# R_03 — decode policy (`full|draft`) + parity / latency harness re-review

## 0. Verdict

The **default path is genuinely unchanged**: with `decode="full"` there is no extra
decode, no changed resize/crop order, no RNG consumption and no extra forward. The
four 60-epoch arms (all configs have no `decode` key → `full`) are **not
invalidated**, and old v1/v2 caches still load as `full`. Checkpoint coupling is
also correct: `best.pt` carries the policy, and `predict`/`evaluate` use it with no
independent default.

However the **acceptance tooling has a false-pass path and the draft+crop claim is
false**, so the decision artefacts this task produces cannot yet be used to switch
the submission to `draft`. Verdict: **issues** — no code regression for the running
arms, but majors F1–F6 must be fixed before the draft ship decision.

## 2. Answers to the review questions

### 2.1 Default invariance (`decode="full"`) — **yes**

- `load_rgb` full path is the old sequence exactly: `Image.open` → `exif_transpose` → `convert("RGB")` → `load()`. The draft branch and the 4S thumbnail are both short-circuited by `decode != "full"`. The only additions on the full path are two validations (`decode` enum, `image_size > 0`).
- `CropBlackBorder` was split into `bbox()` + `__call__`, but the arithmetic is identical: same array scan, same 10 % area guard, same `round(max(dx,dy)*margin)`, same clipped box. `build_preprocess` is untouched.
- `FundusDataset.__getitem__` calls `load_rgb(path, self.decode, self.image_size)`; with `full` this is the same call. `build_transform` is unchanged.
- No RNG is touched in decode/crop/letterbox; sampler/augmentation generators are unchanged; `seed_everything` is unchanged.
- `preprocessing_spec` gains `"decode": "full"`; `ImageCache` accepts v1 (`letterbox_v1`) and v2 manifests as `full` via `setdefault`, so existing caches still load. New caches are v3; no numeric effect.
- Trainer threads `decode` into metadata, `ImageCache` and `FundusDataset`; for `full` the pixels are identical. `metadata.json`/`config.json` gain a field only.
- No draft leak found: no config under `configs/` contains `decode` (checked), so all four arms are full. `audit_samples` defaults its loader to `load_rgb(path)` (full), so a draft run's `verify_images` audit still decodes full — slower, but not a correctness leak.
- The only default-path compatibility edge is `_resume_compatible` now comparing `decode`; an old `last.pt` plus an old config file both default to `full`, so it matches. The running arms were started from this commit anyway.

### 2.2 Draft correctness — **geometry holds before crop; the crop/fallback claims do not**

- Pillow chooses `scale = min(w//S, h//S)` and the largest `s ∈ {8,4,2,1}` with `s ≤ scale`; decoded size is `ceil(w/s) × ceil(h/s)`. Therefore both decoded dimensions are `≥ S` whenever the source short side is `≥ S`, and a square target makes the guarantee rotation-invariant: `draft` is called **before** `exif_transpose` (required, because transposing copies/loads and makes `draft` a silent no-op); after a 90° EXIF rotation both dimensions are still `≥ S`. It never upscales the source.
- Sources with a short side `< S` are not scaled by `draft` (scale 1); letterbox upscales them exactly as the full path always did — no regression, but the docstring's absolute "short side ≥ S" is wrong (the tests' own 300×200 fixture disproves it).
- **Crop breaks the property** (F2): the scale is chosen before `CropBlackBorder`; a crop can leave a field whose long side is `< S`, and the letterbox then upscales it. Even when it does not upscale, the effective field resolution is much lower than the full path. This is the mechanism behind the measured 6/100 images above 0.010.
- Non-JPEG: `draft` is skipped (`image.format == "JPEG"` guard) and the 4S thumbnail only shrinks; pixels are therefore identical to full for images `≤4S`, and a bilinear downscale otherwise (draft mode only). The thumbnail is **not** a memory guard (decode already allocated the full image), and it also fires for extreme-aspect JPEGs whose long side exceeds 4S despite a valid draft.
- CMYK / grayscale JPEG: `draft` operates on the DCT/decoder side and `.convert("RGB")` still happens after decode, so colour handling is unchanged; the modern implementation does not reject `CMYK`/`L`, and the `try/except` keeps a plugin-level failure safe. The `AttributeError` catch is dead code (`Image.Image.draft` always exists); a cleaner fallback is to re-open and take the full path if `draft` raises, so a partially mutated image can never be decoded. In practice the implementation mutates `_size` only immediately before `tile`/`decoderconfig` with no raising call in between, so the risk is theoretical.
- Extreme aspect: as long as the short side is `≥ S`, both dims stay `≥ S`; scale is capped at 8, which is fine. The failure mode is the same small-source case as above.

### 2.3 Cache identity — **v3 semantics correct; manifest crash-safe (fail-closed)**

- v1 → `letterbox_v1` + `full`; v2 → stored preprocessing + `full`; v3 → `preprocessing.decode` must exist and match the top-level `decode`, and the requested policy must match both. Draft↔full is rejected in both directions (tested). Identity also includes `image_size`, source root, CSV sha256 and per-file size/mtime, so a stale cache cannot silently pair with changed sources.
- `cache-images` builds all `.npy` files first (atomic writes) and writes `manifest.json` **last** via `save_json` → `atomic_write` (temp file + `os.replace`). A crash before the manifest leaves no manifest and the next load fails closed; a partially written manifest cannot be observed. The only residual is that a failed build leaves an un-retryable directory (`mkdir(exist_ok=False)`) — pre-existing.
- A v3 manifest with the `preprocessing.decode` key removed by hand would be read as `full` (`setdefault`); only reachable by manual editing, low risk.
- The cache records the policy but not the Pillow version; combined with F6 this is the remaining identity gap for draft caches.

### 2.4 Checkpoint coupling — **correct; post-hoc switching is impossible by design**

- `inference_payload` stores `config.to_dict()`, which now includes `decode`; `load_model` → `Config.from_dict` (old payloads default `full`). `_inference` builds the dataset with `config.data.decode` and `image_size` from the checkpoint; there is no CLI `--decode` on `evaluate`/`predict`. So a draft-trained model cannot be accidentally scored with full, and a full model cannot be scored with draft.
- `_resume_compatible` rejects a policy change on resume; `initialize_model` (fine-tune from `best.pt`) does not compare data config, so mixing is possible there — acceptable for a deliberate fine-tune but should be documented/recorded.
- The flip side of the strong coupling: a post-hoc "measure draft on a full-trained model, then serve draft" idea has no code path — `predict` would still run the checkpoint's `full`, so it needs a deliberate override or the documented task-09 retrain. The parity script can *measure* the post-hoc scenario, but `predict` cannot execute it. Since the documented plan is a draft retrain, the §3/§4 acceptance command's `--decode draft` override is only correct once the measured checkpoint itself has `decode=draft` (F4).
- Traceability gap: `evaluate`/`predict` outputs do not record which decode policy produced them.

### 2.5 Parity gates — statistically weak as an acceptance gate

- Same images/order: yes (full split, shuffle off, names compared). Same crop config: **not for tensor parity when `--config` is omitted** (F1). p95 over per-image deltas: yes, but it is the p95 of per-image **mean** |Δ|; localised errors (max 2.0, element-wise p99 0.227 with crop) are reported and not gated.
- AUROC gate: same split, checkpoint-derived crop, but fp32, fixed 0.001, no CI. On 5,849 valid rows the paired delta is deterministic but the 0.001 threshold is below the sampling resolution of a valid-set AUROC estimate; it is a policy choice, not a statistical test. Also AUROC alone is insensitive to calibration and threshold flips.
- The 0.010 tensor threshold is a smoke test, **not** calibrated to AUROC. A marginal pass can still shift AUROC because the error is not white noise: it is concentrated in the large/×8 images, and it changes the crop framing (0.82 % bbox drift), which is exactly the covariate a crop-trained model is sensitive to. The realistic risk of a marginal pass is non-zero; measure AUROC and per-row probabilities on the deployment preprocessing instead of relying on the pixel gate.

### 2.6 Latency harness honesty — mostly honest, with four optimism sources

- Honest: reads each file, decodes, crops/letterboxes, normalises + H2D, runs a batch-1 forward, computes sigmoid/CSV row, with CUDA sync around transfer/forward; no DataLoader; p50/p95/p99/max; cold start reported separately; artifact size from the checkpoint file; versions in JSON.
- Optimistic: (i) `--decode` override (F4); (ii) `model.half()` vs deployment autocast (F5); (iii) the page cache is warmed by the warmup loop over the first `warmup` images and the same chosen set (read p50 0.66 ms; a cold judge read of a multi-MB file can be 10–40 ms; only the first image's cold total is reported); (iv) the p95 excludes process start, model load, CUDA context and cuDNN warmup (2.8 s cold, disclosed). The non-T4 `PASS` (F8) and the 2.0× forward-only projection (89.7 ms p95, ~10 ms headroom; +50 % CPU → ~108 ms, admitted in the docs) are the remaining acceptance traps.
- The 20-image report (`--images 20 --include-largest 10`) makes the quoted p95 essentially a near-max of 20; the acceptance command correctly uses 200, so insist on that for the final number. The largest-10 selection is conservative, not optimistic.
- CPU numbers were taken on a loaded shared host (load 12–19), which is conservative; they are still not the judge host's per-core performance.

### 2.7 Ship-draft conditions and the cheapest experiment

The four in-flight arms stay valid (all `full`). The final submission can be either:

**Path A — post-hoc draft inference from a full-trained checkpoint** (cheapest, but currently not executable by the CLI):
1. Fix F1/F3 in the parity script; run it with the **checkpoint's** crop config on the full valid split.
2. Require |ΔAUROC| ≤ 0.001 with a paired bootstrap CI, per-row probability deltas and threshold-flip rate acceptable, and bbox drift/disagreement gates clean.
3. Add an explicit, logged inference override (or decide against Path A), because `predict` cannot serve draft otherwise.
4. Verify the judge's Pillow version (F6) and measure T4 + judge CPU with the actual shipping invocation, not `--decode draft` alone.

**Path B — draft-trained submission** (task 09):
1. Rebuild the draft cache (or decode live) with the same Pillow as the judge; the cache/live pixels must match.
2. Compare the draft arm's valid AUROC to its full-decode twin (paired, not to a different arm) and keep the T4/size gates.
3. The tensor gate is then a consistency smoke test, not the primary ship gate; the train/serve mismatch of Path A disappears.

**Cheapest experiment now** (no checkpoint yet): wait for the first arm's `best.pt`; on an idle GPU run the fixed `check_decode_parity --checkpoint <best.pt> --split valid` (full split, ~2–4 min) plus a **test-split, label-free probability-delta pass** (add support in `03.1`) to estimate Path A cost; add a `--split test` mode and compare `|Δp|`, rank correlation and 0.5-flip rate. If Path A fails or is marginal, a 3–5 epoch draft fine-tune from the best full arm is the cheapest Path B. Do not start a 60-epoch draft arm before that measurement.

## 3. Architecture / contract impact

- `DataConfig.decode` (default `"full"`) now participates in config/checkpoint/cache identity. `best.pt` carries it; `predict`/`evaluate` own it.
- `dataset.load_rgb(path, decode="full", image_size=384)` extended; `FundusDataset` gains `decode`/`image_size`; `preprocessing_spec` gains `decode`; cache manifest v3 (v1/v2 read as full); `ImageCache` gains `decode`; trainer threads the value into metadata/cache/dataset; `CropBlackBorder.bbox` extracted (numerically identical); new `utils.percentile`; new scripts and docs. No change to the `best.pt` format version, inference output schema, or default numerics.
- New contract to be aware of: **inference policy is checkpoint-owned and has no CLI override**, so the "switch decode at inference" idea needs an explicit code change.
